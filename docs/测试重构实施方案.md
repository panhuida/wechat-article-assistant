# 测试重构实施方案

## 目标

本方案用于将项目测试体系重构为可持续回归的结构，重点解决以下问题：

- 测试过度依赖全局状态，隔离性不稳定
- 关键链路缺少自动化覆盖，尤其是登录、采集、下载和 CLI
- 手工测试与自动化测试割裂，无法支撑持续回归
- 当前测试结构与项目实际架构耦合不清，扩展成本高

重构后的目标是：

- 默认测试不依赖真实微信登录、真实网络、真实浏览器
- 大部分回归由 `unit + integration + contract` 测试兜底
- 少量真实环境验证保留在 `e2e` 或 `manual`
- 测试基建围绕当前 Flask + 原生 SQLAlchemy 架构设计

## 分层设计

### 1. unit

目标：验证纯业务逻辑和纯函数转换。

覆盖范围：

- `utils`
- 时间解析
- 参数校验
- HTML 清理和 Markdown 转换中的纯函数
- 小型 service 方法

要求：

- 不访问真实数据库
- 不访问真实网络
- 不启动真实浏览器

### 2. integration

目标：验证模块协作。

覆盖范围：

- `routes + services + database`
- Flask Test Client + 测试数据库

要求：

- 使用测试数据库
- mock 掉微信接口、浏览器登录、真实下载请求

### 3. contract

目标：验证外部响应和内部解析契约。

覆盖范围：

- 微信接口 JSON 响应解析
- 文章 HTML 解析
- 发布时间/IP 信息注入
- 文章文件命名规则

要求：

- 使用固定样本文件
- 不访问真实网络

### 4. e2e

目标：保留少量关键端到端冒烟链路。

建议只保留：

- 登录后搜索公众号
- 采集一页文章
- 下载一篇文章

要求：

- 默认不在每次提交都跑
- 只在手动触发或定时任务中运行

## 生产代码需要先做的改造

### 1. 应用工厂支持测试配置注入

将 `create_app()` 改为支持 `test_config`，让测试可以注入：

- `TESTING`
- `DATABASE_URL`
- `LOGIN_MODE`
- `DOWNLOAD_DIR`
- `SESSION_FILE`

### 2. 数据库配置入口显式化

当前数据库连接依赖模块级全局 `engine` 和 `SessionLocal`。需要提供显式重配置入口，例如：

- `configure_database(database_url: str) -> None`

这样测试可以安全切换数据库，而不是直接 monkeypatch 模块内部对象。

### 3. 抽离外部依赖 adapter

建议新增：

- `adapters/wechat_api.py`
- `adapters/auth_gateway.py`
- `adapters/storage.py`

职责：

- 封装 `requests.get`
- 封装 `WechatAuthenticator`
- 封装下载目录和文件写入

### 4. 抽离纯解析函数

从下载和采集流程中剥离纯函数模块，例如：

- `parsers/html_to_markdown.py`
- `parsers/publish_info.py`
- `parsers/wechat_response.py`

这样 unit/contract test 可以直接覆盖核心逻辑，不依赖 service 副作用。

## 测试基建设计

### 数据库策略

不建议在当前架构下默认使用 `sqlite:///:memory:`。

建议：

- 单元测试不碰数据库
- 集成测试使用每个测试独立的临时 sqlite 文件
- 每个测试 `create_all -> run -> drop_all`

原因：

- 当前项目使用原生 SQLAlchemy
- 多个 session/连接下，文件型 sqlite 比内存 sqlite 更稳定

### conftest.py 设计原则

应提供：

- `test_config`
- `app`
- `client`
- `db_session`
- `tmp_download_dir`
- 未来可扩展的 `fake_wechat_api` / `fake_auth_gateway`

原则：

- 每个测试函数独立数据库
- 默认不访问真实网络
- 默认不依赖已有登录状态

## 样本驱动测试

在 `tests/fixtures/` 中保存真实样本：

### API 样本

- 微信搜索接口成功响应
- 微信搜索接口登录失效响应
- 文章列表成功响应
- 文章列表失败响应

### HTML 样本

- 普通文章
- 纯图片文章
- 带发布时间/IP 信息的文章
- 结构异常的文章

### Session 样本

- 有效 session
- 失效 session

这些样本用于 contract tests，确保解析逻辑面对真实结构时稳定输出。

## 首批优先补的测试

### 1. contract

优先新增：

- `test_html_to_markdown.py`
- `test_publish_info.py`

覆盖：

- 标题、段落、列表、引用、代码块
- 纯图片内容
- 发布时间提取
- IP 归属地提取
- 原文链接注入
- 异常 HTML 降级

### 2. integration

优先新增：

- `test_article_routes.py`
- `test_wechat_routes.py`

覆盖：

- 参数校验
- 404/空请求体/空列表
- 登录状态分支
- 会话失效分支
- 下载、删除、采集、搜索等关键端点

### 3. unit

优先新增：

- `test_cli_parsing.py`
- `test_wechat_service_db.py`
- `test_download_service.py`

覆盖：

- CLI 参数解析
- 时间边界
- 全部失败退出码
- duplicate fakeid
- 下载结果标记

## 工厂方法

为了减少样板代码，建议增加 `factories/`：

- `build_account(**overrides)`
- `build_article(**overrides)`

好处：

- 测试数据默认值统一
- 更容易表达边界条件
- 测试代码更短更稳定

## 标记策略

建议在 `pytest` 中统一 marker：

- `unit`
- `integration`
- `contract`
- `e2e`
- `slow`
- `manual`

推荐执行策略：

- 本地默认：`unit + integration + contract`
- PR：同上
- 夜间任务：增加 `e2e`
- 手工验证：运行 `manual`

## CI 建议

建议至少拆成三个 job：

### 1. lint-type

- `ruff check`
- `pyright` 或 `mypy`

### 2. test-fast

- `pytest -m "unit or integration or contract"`

### 3. test-e2e

- 手动触发或定时运行
- 使用专用环境变量和受控登录状态

## 覆盖率策略

不建议一开始就硬性设置全局 `80%`。

推荐分三步：

1. 先生成覆盖率报告，不设门槛
2. 对关键模块单独设阈值
3. 再逐步增加全局阈值

优先关注的模块：

- `services/download_service.py`
- `routes/article_routes.py`
- `routes/wechat_routes.py`
- `cli.py`

## 实施顺序

建议按以下顺序推进：

1. 改 `create_app(test_config=...)`
2. 改数据库配置入口
3. 抽离 adapter
4. 抽离 parser 纯函数
5. 重写 `tests/conftest.py`
6. 先写 contract tests
7. 再写 integration tests
8. 最后整理 e2e/manual tests

## 完成标准

测试体系重构完成后，应满足：

- 默认测试不访问真实网络
- 默认测试不依赖微信登录态
- 关键路由、下载流程、CLI 分支具备自动化回归
- 手工测试只保留少量真实端到端验证
- 新功能能自然归入某一层测试，而不是继续堆积在 `manual/`
